## 二、配置节（ReliefConfig 扩展）

在 ReliefConfig.cs 新增 v0.91 配置字段，键前缀 `Relief.Problem.`，沿用现有 `IConfigManager` 覆盖机制（MODULE = "Content.Governance"）。全部字段有代码默认值，外部配置缺省时行为即默认值。

| 字段 | 默认值 | 单位 | 语义 |
|------|--------|------|------|
| `ProblemLegitimacyWearPolitical` | 0.002 | /s | Political 级问题：合法性磨损速率 |
| `ProblemLegitimacyWearCrisis` | 0.005 | /s | Crisis 级问题：合法性磨损速率 |
| `ProblemOpinionWearPolitical` | 0.0005 | /s | Political 级问题：民望侵蚀速率 |
| `ProblemOpinionWearCrisis` | 0.001 | /s | Crisis 级问题：民望侵蚀速率（Law + 对应轴话题） |
| `ProblemResolvedLegitimacyRise` | 0.01 | 一次性 | 问题消退：合法性回升 |
| `ProblemResolvedOpinionRise` | 0.01 | 一次性 | 问题消退：民望回升 |
| `ProblemCooldownDiscountCommon` | 0.8 | 乘数 | Common 级：同轴冷却折扣（八折冷却） |
| `ProblemCooldownDiscountPolitical` | 0.6 | 乘数 | Political 级：同轴冷却折扣（六折） |
| `ProblemCooldownDiscountCrisis` | 0.5 | 乘数 | Crisis 级：同轴冷却折扣（五折） |
| `ProblemBudgetRegenPolitical` | 0.02 | /s | Political 级：预算自动回补（= BudgetRegenPerSec，急事急办） |
| `ProblemBudgetRegenCrisis` | 0.05 | /s | Crisis 级：预算自动回补 |

约定：
- 磨损/回补类速率为**每秒**，消费者 Tick 时乘 deltaTime。
- PublicOpinionSystem 无 deltaTime（GameClock 间隔结算），按其 `UpdateInterval` 配置常数换算为每结算间隔一次扣除（见第四节）。
- Common 级问题：仅冷却折扣生效，无合法性/民望磨损，无预算回补。

## 三、测试缝：等级→反应量纯函数

三个消费者共用同一模式：把"等级→反应量"映射提为可测纯函数，不依赖 Unity Time / EventBus / ServiceResolver。输入 `IEnumerable<EmergentProblem>` + `ReliefConfig`，输出速率/折扣。单测直接测纯函数，无需构造 EmergentProblemSystem。

各消费者新增（或复用）的纯函数：

| 函数 | 归属 | 逻辑 |
|------|------|------|
| `GetEmergentWearRatePerSec(problems, config)` | Legitimacy（internal static） | 遍历问题，Political → +`ProblemLegitimacyWearPolitical`，Crisis → +`ProblemLegitimacyWearCrisis`；按轴聚合取最高（防御性——当前 `ActiveProblems` 为字典结构，每轴至多一个活跃问题）；**多轴并存时各轴独立叠加**；Common 及以下为 0 |
| `GetAxisCooldownDiscount(problems, axis, config)` | GovernanceResponseSystem（internal static） | 该轴最高等级 → 1.0（无问题）/ 0.8 / 0.6 / 0.5 |
| `GetEmergentBudgetRegenPerSec(problems, config)` | GovernanceResponseSystem（internal static） | 全局最高等级 → 0 / 0.02 / 0.05 |
| `GetEmergentOpinionErosion(problems, config, interval)` | PublicOpinionSystem（internal static） | 问题轴映射话题，速率 × interval 换算；Law 话题按全局最高等级侵蚀 |

## 四、三消费者接线

### 4a. Legitimacy

- `Initialize()` 解析 `_problemSystem = ServiceResolver.OptionalService<EmergentProblemSystem>()`（空安全，OptionalService 已为项目标准模式）。
- `Tick(deltaTime)` 末尾追加：

```csharp
float wearRate = GetEmergentWearRatePerSec(_problemSystem?.ActiveProblems.Values, _config);
if (wearRate > 0f) ApplyWear(wearRate * deltaTime);
```

- 消退正反馈：`ProblemResolvedEvent` → `ApplyChange(ProblemResolvedLegitimacyRise)`。订阅位置见 4d。

### 4b. PublicOpinionSystem

- 无 deltaTime，按 GameClock + `_config.UpdateInterval` 结算。**不引入第二时间基准**：在 `Update()` 现有各话题结算中，把侵蚀量以"每结算间隔"为单位合并进 `change`：

```csharp
float perInterval = 每秒速率 × _config.UpdateInterval;  // 换算常数
```

- 施加话题：问题轴映射话题（复用现有 `PressureDemand.MapAxisToTopic`，GovernanceResponseSystem.ApplyReliefEffect 已使用同映射）+ Law 话题（按全局最高等级）。
- 消退正反馈：`ProblemResolvedEvent` → `ModifyOpinion(Law + 对应轴话题, +ProblemResolvedOpinionRise)`。

### 4c. GovernanceResponseSystem

- `Initialize()` 解析 `_problemSystem`（空安全）。
- `Tick(deltaTime)` 追加：

```csharp
float regen = GetEmergentBudgetRegenPerSec(_problemSystem?.ActiveProblems.Values, _config);
if (regen > 0f) _budget = Mathf.Min(_budget + regen * deltaTime, _config.GlobalBudget);
```

- `PerformRelief` 同轴冷却检查改为折扣判定：

```csharp
float discount = GetAxisCooldownDiscount(_problemSystem?.ActiveProblems.Values, action.TargetAxis, _config);
if (Time.time - last < (_config.PerAxisCooldown * discount)) → blocked
```

- 原方案 A 中"解除同型冷却"一项**取消**——保持 Tradeoff 简单，折扣 + 预算回补已足够表达"急事急办"。
- 消退：`ProblemResolvedEvent` → 清除该轴冷却相关累加（`_axisRecentCount[axis]` 归零、`_axisLastReliefTime` 删除该轴键）。

### 4d. 事件订阅位置

全部集中在 GovernanceModule.cs：
- 新增 `WireProblemEvents()/UnwireProblemEvents()`，与现有 `WireLegislationEvents()` 并列，订阅 `ProblemResolvedEvent`。
- 回调分发：合法性回升 → `_legitimacy.ApplyChange(...)`；民望回升 → `IPublicOpinionSystem.ModifyOpinion(...)`；清冷却累加 → `GovernanceResponseSystem` 新增公开方法（如 `ClearAxisCooldownAccum(SituationAxis axis)`）。
- 分层原则保持：**模块负责订阅，服务负责计算**。

### 4e. 数据流

```text
EmergentProblemSystem (5s tick, priority 220)
  ├─ ActiveProblems（IReadOnlyDictionary<SituationAxis, EmergentProblem>）
  │     ├─→ Legitimacy.Tick (1s, Governance) ──── ApplyWear(rate × dt)
  │     ├─→ PublicOpinionSystem.Update() ──────── 侵蚀并入各话题 change
  │     └─→ GovernanceResponseSystem.Tick (1s) ── 预算回补 + 同轴冷却折扣
  └─ ProblemResolvedEvent ──→ GovernanceModule.WireProblemEvents
        ├─→ Legitimacy.ApplyChange(+0.01)
        ├─→ PublicOpinionSystem.ModifyOpinion(+0.01)
        └─→ GovernanceResponseSystem.ClearAxisCooldownAccum(axis)
```

## 五、触发时序与快照

- EmergentProblemSystem 5s 间隔、priority 220；Governance 1s 间隔、priority 220。消费者最多读到 5s 前的快照——持续式反应下可接受。
- 问题瞬时生灭（小于一次问题 Tick）消费者可能完全看不到：已由 `PersistenceRequired = 30s` 兜底（EmergentProblemSystem 内部），问题最短存活 ≥ 30s，消费者 1s/UpdateInterval 结算必然至少观察到若干次。

## 六、测试清单（TDD，先测后实现）

1. `ReliefConfig` 新增键：默认值与 `IConfigManager` 覆盖生效。
2. `GetEmergentWearRatePerSec`：空集合 = 0；Political 单问题 = 0.002；Crisis 单问题 = 0.005；多轴并存（Political + Crisis）= 0.007（各轴独立叠加）；Common/Trend/Local = 0。
3. `GetAxisCooldownDiscount`：无问题 = 1.0；Common = 0.8；Political = 0.6；Crisis = 0.5；同轴多等级取最高。
4. `GetEmergentBudgetRegenPerSec`：无/Common = 0；Political = 0.02；Crisis = 0.05。
5. `GetEmergentOpinionErosion`：Political 速率 × interval 换算正确；话题映射（劳资紧张 → WorkConditions / 社会动荡 → Law 等）正确；Law 按全局最高等级。
6. `ProblemResolvedEvent` 分发：Mock 发布一次 → 合法性 +0.01、民望 +0.01、该轴冷却累加清除，且各只发生一次。
7. 回归：现有 108 项立法测试保持绿色（本设计不触碰 Legislation / Faction 冻结面；`Legislation` 仅新增 2 个可空字段，`LawTemplate` 仅新增可选 `Stakeholders` 字段）。
8. `EmergentLawGenerator` 候选积累：Common 持续 < 60s 不提交；Political 持续 ≥ 120s 提交且仅一次；Crisis 驳回 180s 后可重提一次；全局 120s 冷却生效。
9. `PoliticalGroupFactory`：同 `axis:group` 键两次调用返回同一实例；组织度累计 +0.05/次。
10. 参数调制与谈判：Severity=0.5 → k=1（等于模板默认）；Severity=1 → k=1.25；Stakeholders 为空的模板跳过谈判；非空时谈判修正随 Severity 单调。
11. `ComputeSupport`：等权 3 群体 + Severity=1 + 无偏置 = 1.0（通过）；群体占比 0.1 + Severity=1 = 0.1（驳回）；+ 偏置 0.15 = 0.25（仍驳回）；群体占比 0.4 + Severity=1 + 偏置 0.15 = 0.55（通过）；执政一票否决路径（否决后走 Rejected 不复算支持度）。
12. 数量控制：PoliticalLaw 达 8 条时生成器转「待容量」；玩家废止 1 条后自动恢复提交。
13. 管线状态机：Propose → 30s Debating → Voting → Enacted 发布 `LawEnactedEvent`（断言事件字段含 Category/含 SourceProblemId/SponsorGroupId 的 LawId）；Rejected 发布 `LawProposalStatusChangedEvent`。
14. 溯源：Enacted 的法律 `SourceProblemId`/`SponsorGroupId` 非空且可反查问题详情；玩家立法的两字段为 null。

## 八、风险与缓解

| 风险 | 缓解 |
|------|------|
| 消费者读到 5s 前快照 | 持续式反应，可接受；见第五节 |
| PublicOpinionSystem 双时间基准（GameClock vs deltaTime） | 换算因子取 `UpdateInterval` 配置常数，不依赖实际 dt |
| 磨损叠加失衡（多轴同爆 → 合法性雪崩） | 各轴独立磨损可叠加，但 Crisis 阈值 0.85 极高且需 120s 持续，多轴同爆概率低；后续 v0.92+ 平衡期可调 `Relief.Problem.*` 配置 |
| EmergentProblemSystem 未注册时消费者 NullReference | 全部经 `OptionalService` 空安全解析；测试缝纯函数接受 null 集合 |
| 法律无限增长（涌现法案泛滥） | 双重防护（9.8）：同问题去重、同轴单提案、全局 120s 冷却、PoliticalLaw 总量上限 8 条 + 待容量轮询 |

## 九、涌现法律生成机制（v0.91 扩展）

> 本章实现"涌现问题 → 政治议程 → NPC 提案 → 简化审批 → 成法"完整因果链。遵守 SPEC 1.2 PoliticalLaw 语义：不经玩家直接操作，但执政派系保留一票否决；成法后复用冻结事件 `LawEnactedEvent`，自动获得既有宏观接线（GovernanceModule.OnLawEnacted → ApplyLawRelief → 合法性/民望回升）。

### 9.1 阶段触发与候选积累

| 阶段 | EmergentProblem 级别 | 系统行为 |
|------|---------------------|---------|
| 观察 | Level 0–1（Local/Trend） | 不进入政治系统 |
| 候选积累 | Level 2（Common），持续 ≥ 60s | 加入 `EmergentLawGenerator` 候选集，开始积累持续时长 |
| 提交 | Level 3（Political），候选持续 ≥ 120s | 生成提案并提交简化涌现管线；**同一 SourceProblem 仅提交一次**（去重） |
| 危机重提 | Level 4（Crisis） | 若该问题已提交过且前次被驳回 ≥ 180s，允许同一方案系（同轴+同模板）重新提交一次 |

全局冷却：任意一次涌现提交后 120s 内不再提交新提案（防爆发式涌入）。

### 9.2 Sponsor（提出者）的生成与复用

- 来源：问题 `AffectedGroups`（EmergentProblem 既有字段，如「工人」「企业主」「工会」）。
- `PoliticalGroupFactory`（新建，Politics 命名空间）按「问题轴 + 影响群体」生成键 `axis:group` 查找既有 PoliticalGroup（v0.90 数据层已就绪）；不存在则创建最小政治组织：
  - `Name` 由群体名派生（如「劳资紧张·工人联合会」）
  - `SourceIssue` = 问题 Id（复用 v0.90 预留字段「催生该组织的议题 ID」）
  - `Goals` 初始单目标：解决该轴问题（描述串）
  - `Organization` 起始组织度 = 0.1 + Severity × 0.2
- 复用规则：同一 `axis:group` 键在殖民地生命周期内只建一次；后续同键问题复用并累计组织度（+0.05/次）。
- SPEC 合规：PoliticalGroup 冻结字段（10 个）只赋不改名；不触碰 FactionData、不迁移既有派系。

### 9.3 法律内容确定：轴 → 模板 + 参数调制

- **模板映射表**（`EmergentLawGenerator` 内置静态表，实现时经 `LawTemplate` 库实际类别校准）：

| 问题轴 | 模板类别（LawCategory） |
|--------|------------------------|
| LaborTension | Labor（劳动法） |
| SocialUnrest | Security（治安法） |
| IdeologicalSplit | Religion（宗教法） |
| MoralFatigue | Welfare（福利法） |

- **参数调制**：读取所选模板的基础参数，按问题强度调制：

```text
调制系数 k = 1 + (Severity - 0.5) × 0.5        // Severity∈[0,1]，k∈[0.75, 1.25]
最终参数 = 模板基础参数 × k
```

- 每条生成的法律强制：`Level = PoliticalLaw`、`AuthorityCost = 0f`、`EnforcementMode = AgencyRequired`（SPEC 1.2 默认值，锁定不调）。
- **谈判修正**（见 9.5）在调制结果之上做第二次修正，保证参数至少部分来自"过程"而非纯模板（v2 计划书 §18 验收条款）。

### 9.4 简化涌现管线（新建 EmergentLawPipeline）

与现有管线并行且独立，状态机：

```text
Propose ──→ Debating(30s, 兼谈判结算) ──→ Voting(简化表决) ──┬──→ Enacted ──→ 发布 LawEnactedEvent
                                                              └──→ Rejected ──→ 发布 LawProposalStatusChangedEvent
```

- 新建 `EmergentLawPipeline`（Legislation 命名空间），由 EmergenceModule 或 LegislationModule 注册到 UnifiedScheduler（5s tick，priority 225，位于 EmergentProblem 之后）。
- 不消费玩家输入；与现有 LegislationManager 的完整管线零代码交集（避免扰动既有审批）。
- Voting 后不再设独立 FinalValidation 阶段（简化；LawValidator 基础校验在 Propose 时执行一次）。

### 9.5 谈判结算（Debating 兼作）

- 输入：问题 `AffectedGroups` + 模板 Stakeholders 声明。
- `LawTemplate` 新增可选字段 `Stakeholders`：声明诉求参数列表 `{ Param, Direction(+1/-1), Amplitude }`（如：企业主 → ComplianceCost 方向 -1（压低成本诉求）；工人 → SafetyBonus 方向 +1（抬高保障诉求））。SPEC 冻结只锁 `DefaultLevel` 字段名，新增字段合规；为空时跳过谈判、直接按 9.3 调制参数进 Voting。
- 结算公式（对每个 Stakeholders 声明逐项应用）：

```text
施加力度 t = 0.5 + Severity × 0.5        // t ∈ [0.5, 1.0]，问题越严重诉求越强势
final = tuned × (1 + Direction × Amplitude × t)
其中 tuned = 9.3 参数调制结果；Amplitude = 该参数允许的最大偏离幅度（如 0.3）
```

- 语义：每个诉求方只影响自己声明的那个参数（方向与幅度由声明限定），Severity 决定诉求落实程度；问题越严重，法案越偏离模板默认值。
- 谈判结果写入法律参数（不另存 NegotiationHistory——v0.93 谈判深层化时再落盘完整历史）。

### 9.6 简化表决（Voting）

```text
支持度 = Σ 受影响群体人口占比 × 问题严重度
       + RulingFaction 偏置（执政派系对该类别立法有偏好时 +0.15，否则 +0）
通过阈值 = 0.5
否决权：执政派系（RulingFactionService）可在 Voting 期一票否决 → Rejected（SPEC 1.2「执政否决 VetoLaw，表决期」语义保持）
```

- 群体人口占比：**恒等权**（每组相同权重）。IFactionSystem 为 v0.90 冻结对象（7 成员签名不可改）且无人口占比接口，v0.91 不为其新增成员；等权回退即为实际行为。
- 支持度计算提为纯函数（可测）：`ComputeSupport(AffectedGroups, severity, populationShares, rulingBias)`。

### 9.7 溯源（Legislation 新增 2 字段）

- [Legislation 模型] 新增可空字段（SPEC §3 冻结条款明确允许新增字段）：

| 新字段 | 类型 | 语义 |
|--------|------|------|
| `SourceProblemId` | string（可空） | 来源问题 Id（`EmergentProblem.Id`）；玩家立法为 null |
| `SponsorGroupId` | string（可空） | 提出组织 Id（PoliticalGroup.Id）；玩家立法为 null |

- 存档：随 Legislation 既有 Save/Load 序列化链路落盘（实现时核实现有序列化字段清单是否需显式补充）。
- 因果链查询：`SourceProblemId → EmergentProblemSystem（活跃/历史）→ 问题详情`；历史问题查询留待 EventLedger 侧（v0.93 归因日志深化，v0.91 只保证字段写入）。
- **成法后接线**：Enacted 时发布冻结事件 `LawEnactedEvent`（含 Category），GovernanceModule.OnLawEnacted 既有接线自动泄压 + 合法性回升 + Law 民望回升——**涌现法案不写一行新宏观接线代码**。驳回时发布 `LawProposalStatusChangedEvent`（UI 消费，符合冻结事件表）。

### 9.8 数量控制（双重防护）

1. **提案层**：
   - 同一 SourceProblem 仅提交一次（9.1 去重；Crisis 重提例外）
   - 同轴同时最多一条待审涌现提案（新提案在 Debating/Voting 期间阻塞同轴提交）
   - 全局提交冷却 120s
2. **存量层**：
   - PoliticalLaw 总量上限 8 条（`EmergentLawGenerator` 可配置常量，暂不放入 ReliefConfig——不属治理护栏参数，实现走 `Emergence.Config` 或代码常量）
   - 达到上限时：新提案必须先有旧 PoliticalLaw 被废止（玩家 RepealLaw 或冲突覆盖）才进入 Propose；生成器转入「待容量」状态并轮询（5s）

### 9.9 数据流总览

```text
EmergentProblemSystem (5s)
  └─ Level 2 持续 60s ──→ EmergentLawGenerator.候选集
        └─ Level 3 持续 120s ──→ PoliticalGroupFactory 建/复用 Sponsor
              └─ 轴→模板 + 参数调制 + 去重/冷却/容量检查
                    └─ EmergentLawPipeline: Propose → Debating(谈判) → Voting(正式表) 
                          ├─ Enacted ──→ 写入 SourceProblemId/SponsorGroupId ──→ LawEnactedEvent ──→ 既有宏观接线
                          └─ Rejected ──→ LawProposalStatusChangedEvent（Crisis 可重提）
```

### 9.10 验收准则（对齐 v2 计划书 §18）

- 一条涌现法律可回答：哪条问题（SourceProblemId）→ 哪些群体（AffectedGroups）→ 哪个组织（SponsorGroupId）→ 为什么这些参数（Severity/Persistence 调制 + 谈判折中）。
- 玩家在几个周期内不干预：系统自行完成至少一条「涌现问题 → 法律 Enacted」或「→ Rejected」的资源链事件，且全程无需玩家点击。
- 参数不完全等于模板默认：Severity ≠ 0.5 或存在 Stakeholders 声明的法案，最终参数与模板默认值可观测地不同。
